# Abstract

A payment URI has the form `neptunecash:<address>[?amount=<amount>][&label=<label>][&message=<message>]`. The address is a Neptune Cash bech32m receiving address and carries the network in its human-readable part. Unknown parameters are ignored, parameters prefixed `req-` must be understood, and five names borrowed from other schemes are rejected. Opening a URI never authorizes a payment; the wallet shows the destination and amount and asks.

# Motivation

There is currently no documented standard for expressing "pay this address this amount" as a link or QR code. Every wallet and site that wants payments must invent its own format, and none of them would interoperate. This NIP is Neptune Cash's counterpart to Bitcoin's [BIP 21](https://github.com/bitcoin/bips/blob/master/bip-0021.mediawiki) and unblocks several things at once:

* QR-based receive and send flows in wallets
* Click-to-pay links on explorers, donation pages, and merchant sites
* Deep-linking (`neptunecash:` opens the wallet with a pre-filled send screen)

# Existing practice

The two existing wallets use an undocumented `NPT:` prefix in QR codes, for bare addresses only:

* [neptune-wallet-app](https://github.com/Neptune-Crypto/neptune-wallet-app) generates receive QR payloads as `NPT:<ADDRESS>` (uppercased). It has no scanner.
* [npt-mobile-wallet](https://github.com/zeokin/npt-mobile-wallet) displays the same format, and its scanner strips a leading `npt:` case-insensitively and treats the remainder as the address.

This NIP does not standardize or extend that payload. `NPT:` followed by query parameters is not a payment URI and MUST be rejected. Legacy detection happens before the NIP-2 parser, which rejects `npt:` as a scheme mismatch. A wallet that accepts the legacy payload MUST apply the address rules of parsing steps 3 to 5 to the recovered address, in particular the symmetric-family rejection, and MUST NOT emit a legacy payload carrying an `nsymk`-family string.

Migration: the mobile wallet, the only deployed scanner, SHOULD accept both `neptunecash:` and the legacy address-only payload, indefinitely. Once a mobile release that does so is available, both wallets SHOULD emit `neptunecash:<ADDRESS>` for receive QR codes. Camera apps show either form as text, so nothing else is affected.

# Conventions

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174) when, and only when, they appear in all capitals.

Grammar is given in the ABNF of [RFC 5234](https://www.rfc-editor.org/rfc/rfc5234) with the case-sensitive string extension `%s"..."` of [RFC 7405](https://www.rfc-editor.org/rfc/rfc7405); plain quoted strings are case-insensitive.

Specification, Grammar, Parsing, Test vectors, QR code guidance, Handler registration, and Security considerations are normative. Rationale, the precedent table, and the appendix are informative. Where a rule is stated in more than one normative section, the Parsing steps govern order and error class and the Specification governs meaning.

# Specification

```text
neptunecash:<address>[?amount=<amount>][&label=<label>][&message=<message>]
```

Examples (`<ADDR>` and `<ADDR-ECH>` are the addresses in Appendix A):

```text
neptunecash:<ADDR>
neptunecash:<ADDR-ECH>?amount=1.25&label=Caf%C3%A9
neptunecash:<ADDR>?amount=10&label=Dev%20Fund&message=Invoice%2042
```

## Scheme and query

* The scheme is `neptunecash`, matched case-insensitively. The address-only `NPT:` payload is a wallet convention outside this NIP (see Existing practice).
* The query string, if present, is introduced by `?`; parameters are separated by `&` and may appear in any order. A bare trailing `?` is equivalent to no query string. A fragment (`#`) MUST be rejected.
* Parsers MUST trim leading and trailing ASCII whitespace (the set defined at parsing step 1). Whitespace inside the URI MUST cause rejection; wallets SHOULD report it as a likely transport or link-wrapping error. A space inside a `label` or `message` value is written `%20`.
* A parameter name appearing more than once, known or unknown, MUST cause rejection. Detection runs on raw names before unknown parameters are discarded.

| Component | Case handling |
|---|---|
| Scheme | Case-insensitive |
| Address | Governed by bech32m: all-lowercase or all-uppercase, never mixed |
| Parameter name | Lowercase ASCII only |
| Parameter value | Case-sensitive |
| Percent-encoding hexadecimal digits | Case-insensitive |

## Address

`<address>` is a bech32m receiving address as produced by neptune-core, appearing literally and never percent-encoded. The network is encoded in the address's human-readable part (HRP), so the URI carries no network field; a wallet MUST reject an address whose network does not match its active network.

| Type | HRP base | Mainnet HRP | Length | Rule and disclosure |
|---|---|---|---|---|
| Generation | `nolga` | `nolgam` | 3482 | Allowed. Intended for publication and reuse. Reuse does not disclose amounts or history, but is linkable on-chain (see Security considerations). |
| EcHybrid | `nech` | `nechm` | 168 | Allowed for a request to one payer. An attacker who knows the address and has a quantum computer can read its on-chain history. |
| ViewingAddress | `nview` | `nviewm` | 116 | Allowed for a request to one payer. Anyone who knows the address can read its on-chain history. |
| Symmetric | `nsymk` | `nsymkm` | n/a | MUST NOT appear in a URI. The encoding is the secret key itself. |

Each HRP is the type base followed by one network character, per neptune-core's `network_hrp_char`:

| Character | Network |
|---|---|
| `m` | Mainnet |
| `t` | Testnet. All numbered testnets share this character; the HRP does not identify which. |
| `z` | Testnet-Mock |
| `r` | Regtest |

Reference revision: Neptune Core v0.16.0 (commit `28ff10f8607ac701bc6ee2cb45d0b1ea11448d03`). Implementations SHOULD verify that their Neptune Core revision defines the same HRP bases and network characters, and MUST NOT accept a network character their revision does not define. An address type not listed above MUST be rejected even if a newer Neptune Core revision defines it; only a revision of this NIP adds one. Neptune Core's other bech32m families (viewing keys under `nolgavk` and `nechvk`, UTXO notifications under `utxo`) are not addresses and are rejected as unknown types.

Symmetric-key addresses MUST NOT be generated into or accepted from a URI. A raw `nsymk` encoding grants spending authority to anyone who sees it, and neptune-core uses the same HRP for digest-only display strings, so the whole family is rejected without distinguishing the two. The rejection happens at parsing step 4, before checksum validation and before any payment UI, with an error distinct from a generic invalid-address error (see Security considerations for what the error and the wallet may retain).

An address MUST be entirely lowercase or entirely uppercase; mixed case is rejected before any normalization. After that check an all-uppercase address is treated as its lowercase form for every later step. Implementation note: at the reference revision, `ReceivingAddress::from_bech32m` dispatches on a case-sensitive lowercase prefix and rejects uppercase input, so lowercase before delegating to it.

## amount

Optional. A decimal number of whole NPT, such as `amount=1.25`, requesting that amount. `amount` is the value of the output the recipient receives; the transaction fee is additional and chosen by the payer's wallet. A wallet MUST NOT silently alter the requested amount; an override requires an explicit user action and a visible indication that the amount differs from the request.

* Syntax: digits with at most one `.`; at least one digit on each side of the separator when present; no leading zeros (the integer part is `0` or starts with a nonzero digit); no sign, exponent, grouping, whitespace, or percent-encoding. Trailing zeros are allowed (`10.00` is 10 NPT), so amounts are compared as numbers, never as strings.
* Precision: any amount with at most 30 fractional digits is valid and is a whole number of nau. A 31st and 32nd digit are permitted only when the value is still a whole number of nau, which holds when the 32-digit fraction is a multiple of 25 (1 nau = 25 x 10^-32 NPT); other 31- and 32-digit values are rejected. Generators SHOULD emit at most 30 fractional digits unless they need to name an exact nau count, such as the full value of a UTXO.
* Bounds: greater than zero and at most 42000000, the maximum supply of the current monetary model. If that maximum changes, this NIP is revised; the meaning of existing URIs does not change silently.
* Conversion to nau, the atomic unit (1 NPT = 4 x 10^30 nau), using exact integer arithmetic:

```text
i    = integer part
f    = fractional digits right-padded with zeros to 32 digits (all zeros if absent)
reject if i > 42000000              (bounds i before the multiplication below)
frac = f as an integer (units of 10^-32 NPT)
reject if frac mod 25 != 0          (the amount is not a whole number of nau)
nau  = i * 4 * 10^30 + frac / 25
reject if nau == 0
reject if nau > 42000000 * 4 * 10^30   (i == 42000000 with a nonzero fraction lands here)
```

Every quantity fits in an unsigned 128-bit integer once `i` is bounded; the first bound only guards the arithmetic, the last one is the real maximum. Binary floating point MUST NOT be used at any stage: 1 NPT in nau already exceeds the 2^53 range an IEEE 754 double represents exactly.

Implementation notes for the reference revision: `NativeCurrencyAmount::coins_from_str` is more permissive than this grammar (it accepts signs, `.5`, `1.`, and empty input, and rounds) and MUST NOT be used unvalidated, but a validated amount string MAY be handed to it unchanged; the result is exact. `Display` prints eight rounded decimals and `display_lossless` prints 34, so neither produces a conforming amount; generators format from the nau integer or trim the lossless form to 32 places, which is exact for every whole-nau value.

## label and message

Both optional. `label` names the payee as supplied by the URI creator; `message` describes the payment. Both are unauthenticated, are shown to the payer only, and are never sent on-chain or to the recipient. Wallets MUST NOT treat either as information about the recipient and MUST NOT use either to determine the destination.

* The value is percent-encoded UTF-8 ([RFC 3629](https://www.rfc-editor.org/rfc/rfc3629): no overlong forms, no encoded surrogates, nothing above U+10FFFF), decoded exactly once. `+` is a literal plus sign, never a space; a space is `%20`. Form encoding (`application/x-www-form-urlencoded`) MUST NOT be used on either side.
* An empty decoded value is treated as though the parameter were absent.
* The decoded value MUST be at most 255 bytes.
* The decoded value MUST NOT contain a C0 control (U+0000 to U+001F), DEL (U+007F), a C1 control (U+0080 to U+009F), the line separators U+2028 and U+2029, or the explicit bidirectional formatting characters U+202A to U+202E and U+2066 to U+2069. Other format characters, including zero-width joiners and variation selectors, are legitimately used in some scripts and in emoji and remain permitted.

## Parameters

| Name | Class | Rule |
|---|---|---|
| `amount`, `label`, `message` | Defined | Semantics above |
| `req-*` | Required extension | Unsupported members cause rejection |
| `address`, `address.N`, `amount.N`, `reference`, `memo` | Reserved-unassigned | Rejected. Other schemes give these names destination or recipient-visible semantics; a wallet that ignored one could complete a payment the requester did not intend |
| anything else | Unknown | Ignored |

Parameter names MUST be lowercase ASCII letters, digits, `-`, `.`, `_`, or `~`, matched literally and never percent-decoded; `Amount=1` is invalid, not an unknown parameter. Unknown parameters MUST NOT change the interpretation of defined parameters, and a wallet MUST NOT render the name or value of an ignored parameter. Private parameters SHOULD use a distinctive vendor-specific name (for example `shopname-order`) to avoid colliding with names a future NIP may define.

A future NIP that adds a parameter outside the `req-` namespace MUST define it so that a wallet which ignores it still constructs the intended payment. A parameter whose omission would change the destination, the amount, or the meaning of the payment MUST be defined either as a `req-*` extension or under a reserved-unassigned name above, so that older wallets fail closed. A repeatable value is expressed as one list-valued parameter, since repeated names are rejected. This NIP defines no version parameter; a change to the meaning of an existing URI requires a `req-` parameter or a new scheme.

## Generation and scope

Generators SHOULD emit the scheme and parameter names in lowercase (uppercase is permitted for QR alphanumeric mode, see QR code guidance) in a stable parameter order. No canonical serialization is defined: two URIs may differ as strings and describe the same payment, so implementations compare parsed values, never strings. A future NIP that signs URIs must define its own canonicalization.

Out of scope for this version: multiple recipients, payment references and merchant tracking, recipient-visible memos, fetchable payment requests, and canonical form. The reserved names above keep those extensions fail-closed.

# Grammar

The ABNF is lexical. Checksum, network, address type, amount bounds, duplicate names, and reserved names are checked by the Parsing steps. Alternation carries no precedence: a component whose name is `amount` or matches `reserved-name` is parsed by its specific production, and a string it rejects is classified by the steps, not by which production failed.

```abnf
payment-uri        = scheme ":" address [ "?" [ query ] ]

scheme             = "neptunecash"
                     ; RFC 5234 quoted strings are case-insensitive,
                     ; which is the intended matching rule for the scheme

address            = 1*address-char
address-char       = ALPHA / DIGIT

query              = parameter *( "&" parameter )
parameter          = amount-parameter / reserved-parameter / generic-parameter

amount-parameter   = %s"amount" "=" amount-value
amount-value       = ( "0" / ( %x31-39 *DIGIT ) ) [ "." 1*32DIGIT ]

reserved-parameter = reserved-name "=" value
reserved-name      = %s"address" / reserved-indexed / %s"reference" / %s"memo"
reserved-indexed   = ( %s"address" / %s"amount" ) "." 1*DIGIT

generic-parameter  = name "=" value
name               = 1*name-char
name-char          = LOWER / DIGIT / "-" / "." / "_" / "~"
LOWER              = %x61-7A

value              = *value-char
value-char         = unreserved / pct-encoded / sub-delims-no-amp
                     / ":" / "@" / "=" / "/" / "?"
unreserved         = ALPHA / DIGIT / "-" / "." / "_" / "~"
sub-delims-no-amp  = "!" / "$" / "'" / "(" / ")" / "*" / "+" / "," / ";"
pct-encoded        = "%" HEXDIG HEXDIG

ALPHA              = %x41-5A / %x61-7A
DIGIT              = %x30-39
HEXDIG             = DIGIT / %x41-46 / %x61-66
```

# Parsing

A parser MUST accept URIs of at least 8192 bytes and MAY reject longer ones at step 1. A URI composed solely of defined parameters is at most 5089 bytes. Parsers SHOULD parse then validate rather than pass the URI through a generic URL or form decoder; such a library MAY be used for transport only if it is verified not to normalize `//`, decode, or reinterpret the string first. A library SHOULD expose parsing errors separately from wallet-policy warnings.

A parser MUST evaluate the steps in order, and within a step the checks in the order written, and MUST reject at the first failing check. That check determines the error class named in each step's title; user-facing wording MAY differ. Implementations that expose error classes MUST use these names.

1. **Syntax: preprocessing.** Trim leading and trailing ASCII whitespace: space (0x20), tab (0x09), line feed (0x0A), carriage return (0x0D), vertical tab (0x0B), and form feed (0x0C). Nothing else is trimmed; a no-break space or zero-width space is rejected at step 2. Apply any implementation length limit to the trimmed string.
2. **Syntax: scheme.** Every byte MUST be in 0x21 to 0x7E; any other byte, including internal whitespace and raw non-ASCII, is invalid. The text before the first `:` is the scheme and MUST match `neptunecash` case-insensitively; `neptune`, `web+neptunecash`, and `npt` are scheme mismatches.
3. **Syntax, or Address for case: address form.** A `#` anywhere is invalid. Split the text after the colon into address and query at the first `?`. An empty address is invalid, and so is any address character outside `ALPHA / DIGIT` (this rejects `neptunecash://...` and any percent-encoding). An address containing both uppercase and lowercase letters is invalid (Address class). From here on an all-uppercase address is treated as its lowercase form.
4. **Symmetric-key address.** Let the HRP be the text before the last `1` and the type base the HRP without its final character. If the address has no `1` or its HRP is shorter than two characters, this step does not apply and step 5 rejects the address. If the base is `nsymk`, reject with the symmetric-key error before any further processing (see Security considerations).
5. **Address, or Network mismatch: bech32m.** Validate the bech32m checksum; a bech32 (non-m) checksum is invalid. The 90-character limit of BIP-173 and BIP-350 does not apply, and a library that enforces it by default MUST be configured not to. Then, if the type base is not `nolga`, `nech`, or `nview` (or a base added by a later revision of this NIP), reject as an unknown address type. Then, if the network character does not match the active network, reject as a network mismatch. A parser without the neptune-core decoder performs syntactic validation only; the wallet MUST complete decoding before display.
6. **Syntax: query.** An empty query string is valid; skip the remaining steps. Otherwise split on `&`, then split each component at its first `=`; later `=` characters belong to the value. An empty component, a component without `=`, or an empty name is invalid. Every value, of every component, MUST match the `value` production, each `%` followed by exactly two hexadecimal digits. This runs before any parameter is classified or ignored.
7. **Parameter: names.** Each name MUST match the `name` production. Names are compared byte-for-byte and never decoded.
8. **Parameter: duplicates.** A name appearing more than once is invalid, known or unknown.
9. **Parameter, or Required extension: classification.** A reserved-unassigned name is invalid (Parameter class). A `req-*` name the implementation does not support is invalid (Required extension class). Any other name that is not `amount`, `label`, or `message` is ignored from here on.
10. **Encoding: decoding.** Percent-decode `label` and `message` exactly once, treating `+` literally. The bytes MUST be valid UTF-8 as defined above; lossy replacement is forbidden. `amount` is not decoded.
11. **Amount, or Metadata: values.** Validate `amount` against `amount-value` and convert it as defined in the Specification; failure is an Amount error. An empty decoded `label` or `message` is treated as absent. Otherwise each MUST be at most 255 bytes and contain none of the forbidden code points; failure is a Metadata error. A parser MUST NOT repair or reinterpret a malformed value.

# QR code guidance

A QR code MUST encode the complete URI unaltered; if the chosen QR configuration cannot hold it, the wallet MUST offer the URI as text instead. The following capacity facts are informative and apply to error-correction level L, the level both wallets use:

* An address-only generation payload (`NEPTUNECASH:` plus the uppercased address, 3494 characters) fits from version 36 (161x161 modules) in alphanumeric mode; no level M symbol holds it.
* A parameterized generation URI fits version 40 only with mixed-mode segmentation (an alphanumeric segment for scheme and address, a byte segment for the query), leaving 549 bytes for the query including the `?`. A single-segment encoder drops to byte mode at the first `?` and fails, since version 40 holds 2953 bytes. The 5089-byte maximum URI fits no symbol.
* EcHybrid and viewing-address URIs never need segmentation: even at maximum length (1775 bytes) they fit version 31 in byte mode; the EcHybrid example above (208 bytes) fits version 9.

Uppercasing the scheme and address is what enables alphanumeric mode; `?`, `=`, and `&` are not in that character set, so a query always needs byte mode. Wallets SHOULD default to a generation address and render its QR code large; a request delivered directly to one payer MAY use an EcHybrid or viewing address, subject to Security considerations. A generation-address URI is at least 3494 characters, longer than the message limit of common chat clients; when a pasted link fails the checksum at step 5, the wallet SHOULD say the link may have been truncated or wrapped in transport.

# Handler registration

A wallet that supports links SHOULD register as the operating-system handler for the `neptunecash` scheme if no other handler is registered, so that links open a pre-filled send screen. Registration is unauthenticated: any application, including one impersonating a wallet, can claim the scheme and receive the URIs a user opens, which is a second reason a URI must never carry a secret. A wallet MUST NOT silently take a registration held by another application. On first run it SHOULD NOT request a registration that exists. A wallet that previously held the registration and finds it taken SHOULD alert the user once and offer to restore it, and SHOULD NOT repeat the request if the user declines (the etiquette of Stellar's SEP-0007, sections User Experience and Security Concerns).

Browser-hosted wallets cannot register a bare scheme: `navigator.registerProtocolHandler` accepts only a safelist plus `web+` schemes. This NIP does not define `web+neptunecash:`; a parser rejects it as a scheme mismatch.

# Security considerations

A payment URI is untrusted input: it arrives from web pages, chat messages, and scanned QR codes.

* **Confirmation.** Opening a URI MUST NOT by itself authorize or send a payment. The wallet MUST show the decoded address, the network derived from its HRP, and the amount together with the direction of funds, and require explicit confirmation before signing or broadcasting. The displayed amount MUST NOT show a nonzero request as zero; an abbreviated display SHOULD say it is rounded and offer the exact value.
* **Untrusted text.** `label` and `message` are attacker-chosen. Render each inert (no markup), on a single line with visible truncation, in its own bidi-isolated element, captioned as supplied by the link, and in a region visually separate from the address and amount. The control and bidirectional formatting characters listed in the Specification are guaranteed absent; zero-width and confusable characters are not, so the address, not the label, identifies the payee. Ignored parameters are never rendered.
* **Network mismatch.** A recognized address type on the wrong network is rejected (step 5). Addresses of the XNT fork use the HRP `xntnw` and are rejected as unknown types.
* **The symmetric family.** `ReceivingAddress::to_bech32m` returns the raw key for a symmetric address and its documentation warns it must never be displayed; a wallet that builds URIs through the generic encoder leaks a spending key the moment a symmetric address reaches it. Match on the address type. On the parsing side, once step 4 has matched the family the wallet MUST NOT write the URI or address to any file, database, log, telemetry, or crash report it controls, MUST NOT include it in any error message, dialog, exception, or return value, and MUST NOT place it on the clipboard; the error MAY name the HRP base and SHOULD advise the key's owner to move funds. A secret that reached a URI was exposed before the wallet ran (process arguments, scanner history, clipboard managers); the wallet's obligation is not to add channels.
* **Reuse-sensitive types.** Anyone who knows a viewing address can read that address's on-chain history when on-chain notifications are used, and an EcHybrid address gives the same power to an attacker with a quantum computer. Wallets MUST default to a generation address for receive screens, QR codes, and generated URIs. Generating a URI or QR code that contains an EcHybrid or viewing address MUST require an explicit per-request choice and MUST show, at that moment, that the address is for a single payer and must not be published or reused. Wallets SHOULD avoid persisting or logging such URIs beyond what their operation requires.
* **Address reuse.** Every on-chain UTXO notification carries a public receiver identifier derived from the address, so all on-chain payments to one address are linkable by count and timing by any chain observer, for every address type. Amounts and senders stay hidden. A published donation address accepts this by design; a wallet generating a request for one payer SHOULD derive a fresh address (neptune-core derives addresses deterministically, so fresh ones cost nothing to recover). Because this version defines no payment reference, a fresh address per request is also the only reliable way to match an incoming payment to a request.
* **Deep links.** A URI received while a payment flow is on screen MUST NOT modify that flow; the wallet either discards it or visibly replaces the flow. URIs received in quick succession are coalesced to one.
* **Notification medium.** A URI provides no channel for an off-chain UTXO notification, so payments to a URI address use on-chain notification, the neptune-core default.
* **Test-vector address.** The generation address in Appendix A comes from neptune-core's public test suite; its seed is public and anything sent to it can be spent by anyone. Documentation and demos MUST NOT present it as a real address.

# Rationale

**Scheme name.** Other cryptocurrencies use the project name, not the ticker (`bitcoin:`, `zcash:`, `monero:`), and the project is Neptune Cash, not Neptune: the name is contested by the XNT fork, and operating-system handler registration is one global namespace per scheme, so two wallets registering `neptune:` would fight over links. `neptunecash:` follows the precedent of `bitcoincash:`. The cost is four characters next to a 3482-character address.

**Amount.** Whole NPT with a decimal fraction follows every human-facing scheme and avoids the decimal-shift bugs of smallest-unit amounts (Nano, Ethereum). The nau grid does not align with decimal digits: 1 nau is 2.5 x 10^-31 NPT, so thirty fractional digits always land on the grid and the two beyond them land on it only for multiples of 25. Capping at thirty digits was considered and rejected because the protocol produces amounts that are not multiples of four nau (halving, fee splits) and exposes them through `display_lossless`, so a request for the exact value of a UTXO needs the finer grid; the cost is that a few 31- and 32-digit decimal strings are syntactically well-formed but rejected, which is why generators are told to stop at thirty digits unless they mean an exact nau count. Exact arithmetic is mandatory because the maximum amount, 1.68 x 10^38 nau, is far beyond the 2^53 integers a double represents exactly; BIP 21 and ZIP 321 never needed the rule because their supplies fit. The 42,000,000 bound is a validity rule so that a change in monetary policy is a revision of this NIP rather than a silent change of meaning.

**Metadata cap and control characters.** BIP 21 and ZIP 321 set no length cap, so each wallet invents one and they diverge; 255 bytes is chosen for familiarity, not necessity. Controls, line separators, and bidirectional formatting characters are rejected at parse time because no label needs them (the bidirectional algorithm renders right-to-left text without them), a "neutralize" requirement would mean something different in every wallet, and a stray line break or override in a log line or text widget is a known source of spoofing.

**Fail-closed rules.** Duplicate names are rejected even for unknown parameters so that no two wallets can disagree about which value counts; a repeatable extension uses one list-valued name. Uppercase names are rejected rather than folded (BIP 21 keeps keys case-sensitive; BIP 321 folds them because QR codes are often uppercase) because a parameterized URI cannot use QR alphanumeric mode anyway, and a misspelled `Amount` must fail rather than silently drop the amount. Five names are reserved and rejected because other schemes give them destination or recipient-visible meaning. Symmetric addresses are excluded deliberately, and the whole HRP family with them, so that a future implementer does not add them back believing they were overlooked.
