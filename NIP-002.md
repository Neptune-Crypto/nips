# Motivation

There is currently no documented standard for expressing "pay this address this amount" as a link or QR code. Every wallet and site that wants payments must invent its own format, and none of them would interoperate. This NIP (Neptune Improvement Proposal), Neptune Cash's equivalent of Bitcoin's [BIP 21](https://en.bitcoin.it/wiki/BIP_0021), unblocks several things at once:

* QR-based receive/send flows in wallets

* Click-to-pay links on explorers, donation pages, and merchant sites

* Deep-linking (`neptunecash:` opens the wallet with a pre-filled send screen)

# Existing practice

The two existing wallets already use an undocumented `NPT:` prefix in QR codes, but only for bare addresses, with no additional metadata:

* [neptune-wallet-app](https://github.com/Neptune-Crypto/neptune-wallet-app) generates receive QR payloads as `NPT:<ADDRESS>` (uppercased).

* [npt-mobile-wallet](https://github.com/zeokin/npt-mobile-wallet) displays the same format on the receive screen, and its scanner strips a leading `npt:` case-insensitively and treats the remainder as the address.

No amount, label, or other parameters exist today, and nothing registers an OS-level URI handler. This proposal documents that practice and defines its successor, without breaking anything already deployed: existing address-only `NPT:` payloads keep working in the wallets that already accept them, and the legacy address-only `NPT:` payload is not extended with query parameters by this NIP. Parameterized payment requests use `neptunecash:` and therefore are not interpreted by scanners that only recognize the legacy `NPT:` convention.

# Conventions

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174) when, and only when, they appear in all capitals.

# Terminology

This NIP uses the following terms:

* **Address**: A Neptune Cash receiving address encoded as bech32m. An address identifies the destination for a payment. This NIP permits Generation, EcHybrid, and ViewingAddress types, subject to the restrictions defined below. Symmetric-key addresses MUST NOT be used in payment URIs.

* **Payment URI**: A URI using the `neptunecash:` scheme that contains a Neptune Cash receiving address and zero or more supported query parameters. A payment URI is untrusted input and MUST NOT by itself authorize, sign, or broadcast a transaction.

* **Payment request**: A payment URI intended to request a payment from a payer. A payment request MAY contain an `amount`, `label`, or `message`. A URI containing only an address is still a valid payment URI, but does not specify a requested amount.

* **Public or reusable payment request**: A payment request intended to be published or presented to multiple potential payers. Only Generation addresses are permitted for such requests. EcHybrid and ViewingAddress addresses are intended only for requests shared with a single counterparty, as described in the Security Considerations section.

* **Parameter**: A name/value pair in the query component of a payment URI, such as `amount=1.25`.

* **Known parameter**: A parameter whose semantics are defined by this NIP, currently `amount`, `label`, and `message`.

* **Unknown parameter**: A parameter not defined by this NIP. Unknown parameters are ignored unless they use the reserved `req-` namespace; an unsupported `req-*` parameter causes rejection. Parameters in the reserved `x-` namespace are optional/private extensions and are ignored when unsupported. The reserved-unassigned names `address`, `address.N`, `amount.N`, `reference`, and `memo` are rejected in v1.

# Case sensitivity and normalization

Case handling is defined independently for the URI scheme, address, parameter names, and parameter values. Implementations MUST NOT normalize the entire URI by changing its case before parsing.

| Component | Case handling |
|---|---|
| Scheme | Case-insensitive |
| Address | Governed by bech32m; all-lowercase or all-uppercase only |
| Parameter name | Lowercase ASCII only |
| Parameter value | Case-sensitive unless a parameter definition says otherwise |
| Percent-encoding hexadecimal digits | Case-insensitive |

The scheme may use any combination of uppercase and lowercase ASCII characters regardless of whether query parameters are present:

```text
neptunecash:<address>?amount=1
NEPTUNECASH:<address>?amount=1
NePtUnEcAsH:<address>
```

are all equivalent with respect to scheme matching.

Parameter names MUST consist only of lowercase ASCII letters, digits, `-`, `.`, `_`, and `~`. Any uppercase ASCII letter in a parameter name MUST cause rejection. This provides one stable serialized spelling for each parameter and prevents a misspelled parameter such as `Amount` from silently being treated as an unrelated optional parameter.

Parameter names are matched literally and are never percent-decoded. Percent-encoded hexadecimal digits are case-insensitive as hexadecimal notation, so `%2f` and `%2F` represent the same byte when percent-decoding a value. This does not make parameter names or parameter values case-insensitive.

Existing cryptocurrency payment URI specifications, including Bitcoin, Zcash, Ethereum, and Solana Pay, were considered as references when designing NIP-2. NIP-2 is a Neptune-specific protocol and does not require compatibility with the behavior of any other cryptocurrency. Established practices are adopted where appropriate, while protocol behavior is chosen independently according to Neptune's requirements.

# Specification

A Neptune Cash payment URI has the following general form:

```text

neptunecash:<address>[?amount=<amount>][&label=<label>][&message=<message>]

```

* The scheme is `neptunecash:`, matching the project's full name; see the rationale section for the naming discussion and its resolution. The address-only `NPT:` payload described under existing practice is a wallet-specific convention that was never standardized; wallets MAY keep accepting it for compatibility with deployed QR codes, but this spec does not require it. Migration: wallets that scan QR payloads SHOULD accept both this scheme and the legacy address-only payload. Wallets that generate address-only receive QR codes SHOULD keep emitting the legacy payload while they target scanners that predate this NIP (a deployed scanner that only strips `npt:` cannot read a `neptunecash:` payload), switching to this scheme once the wallets expected to scan their codes accept it; parameterized URIs have no legacy form and always use this scheme. A legacy `NPT:` payload followed by query parameters MUST be rejected; the legacy form is address-only.

* Each query parameter is optional and may appear in any order; the query string, if present, is introduced by `?` and parameters are separated by `&`, as in ordinary URIs. A URI ending in a bare `?` with no parameters is equivalent to one with no query string. A URI containing a fragment (`#`) MUST be rejected: nothing in this scheme uses fragments, and rejecting is safer than silently parsing a different string than the user supplied. Parsers MUST trim leading and trailing ASCII whitespace surrounding the entire URI before parsing, since QR scanners and chat clients sometimes introduce it. Whitespace occurring within the URI MUST NOT be silently removed or normalized and MUST cause a syntax rejection unless it is produced by percent-decoding a permitted parameter value. Wallets SHOULD identify this as a possible transport or link-wrapping error and ask the user to paste or rescan the original link rather than attempting repair.

* A parameter name appearing more than once MUST cause the entire URI to be rejected. First-wins and last-wins parsers disagree silently, and a disagreement about which `amount` counts is a payment bug. This applies to every parameter name, known or unknown: duplicate detection runs over the raw component names before unknown parameters are discarded.

* `<address>` is a bech32m receiving address as produced by neptune-core, appearing literally, never percent-encoded. The network is already encoded in the address's human-readable part (HRP), the prefix before the `1` separator, so the URI needs no separate network field; wallets MUST reject a URI whose address network does not match the active network.

* neptune-core currently defines four receiving-address types. Their disclosure properties differ sharply, and not all of them belong in a payment URI:
| Type           | Mainnet HRP | Length     | Status in this spec                                                          |
| -------------- | ----------- | ---------- | ---------------------------------------------------------------------------- |
| Generation     | `nolgam`    | 3482 chars | Allowed. The only type safe to publish or to reuse across payers.            |
| EcHybrid       | `nechm`     | 168 chars  | Allowed for a request to a single counterparty; see security considerations. |
| ViewingAddress | `nviewm`    | 116 chars  | Allowed for a request to a single counterparty; see security considerations. |
| Symmetric      | `nsymkm`    | n/a        | MUST NOT appear in a URI; see below.                                         |

The following network HRP characters are defined for the Neptune Core revision referenced by this NIP. The monetary-unit relationship is pinned to the referenced Neptune Core documentation; the address/network table is derived from the corresponding address/network implementation.

| HRP character | Network |
|---|---|
| `m` | Mainnet |
| `t` | Testnet |
| `z` | Testnet-Mock |
| `r` | Regtest |

Reference source: Neptune Core `docs/src/consensus/neptune-coins.md` at commit `28ff10f8607ac701bc6ee2cb45d0b1ea11448d03`. Implementations SHOULD verify that their supported Neptune Core revision defines the same address HRPs and network characters before accepting an address type or network not otherwise specified by this NIP.

This table documents the network characters defined by the referenced Neptune Core version. Implementations MUST NOT infer support for networks not defined by their supported Neptune Core version.

* Each HRP is a type base (`nolga`, `nech`, `nview`, `nsymk`) followed by a single network character: `m` mainnet, `t` testnet, `z` testnet-mock, `r` regtest, per neptune-core's `network_hrp_char`. The table lists the mainnet forms. Rejection classification runs in this order: an HRP with base `nsymk` MUST be rejected under the symmetric-address rule regardless of its network character; an HRP with an unrecognized address-type base MUST be rejected as an unknown address type regardless of its network character; a recognized base whose network character does not match the active network MUST be rejected as a network mismatch. Network mismatch therefore applies only when the address-type base is recognized.

* Symmetric-key addresses MUST NOT be used in a payment URI. A raw symmetric-key bech32m encoding contains the secret key itself, so exposing it grants spending authority to anyone who obtains it; and because neptune-core uses the same `nsymk` HRP family for digest-only display strings (`SymmetricKey::to_display_bech32m`), wallets MUST reject the entire family rather than attempt to distinguish secret-bearing from display-only forms. Wallets MUST NOT generate such a URI and MUST reject one on parse, before any payment UI is shown, with an error distinct from a generic invalid-address error; the error SHOULD say that the URI may contain a secret key, not merely that the address type is unsupported.

* The receiving-address enums in neptune-core are marked non-exhaustive, so further types will appear. An address type not listed in the table above MUST be rejected; this spec is to be amended to classify each new type's disclosure properties before wallets accept it, keeping the failure mode closed rather than open.

* Scheme matching is case-insensitive. The address may be all-uppercase or all-lowercase (an all-uppercase scheme and address let the scheme and address portion of the URI use QR alphanumeric mode; see the QR code guidance section); mixed case is invalid per bech32m. A parser MUST validate that the address is entirely lowercase or entirely uppercase before performing any case conversion or normalization. A mixed-case address MUST be rejected and MUST NOT be normalized before validation. Implementation note: neptune-core's generic `ReceivingAddress::from_bech32m` selects the type-specific decoder with a case-sensitive lowercase prefix match and therefore rejects an all-uppercase address; parsers that delegate to it MAY lowercase an all-uppercase address only after the case-symmetry check has succeeded (the type-specific decoders themselves accept uppercase).

* `amount` is optional: a decimal string in whole NPT units (e.g. `amount=1.25`). When present, `amount` specifies the amount requested by the URI. Wallets MUST NOT silently alter the requested amount. A wallet MAY allow the user to override the requested amount only through an explicit user action and MUST make clear in its UI that the amount differs from the URI's requested amount. A wallet MUST display the requested amount before authorization. The grammar is deliberately stricter than neptune-core's own `coins_from_str`, which also accepts negative, fraction-only, trailing-dot, and even empty forms, and which silently rounds input finer than 1 nau instead of rejecting it, so a URI parser MUST NOT delegate to it unvalidated:

  * digits with at most one `.` as decimal separator; at least one digit before the separator and, when the separator is present, at least one digit after it; no leading zeros (the integer part is `0` or begins with a nonzero digit); no sign, no exponent notation, no grouping separators, no whitespace; an empty value is invalid. After the amount passes its syntax and maximum-value checks, the leading-zero rule bounds a conforming amount string at 41 characters. Trailing zeros in the fraction remain valid (`10.00` parses as 10 NPT), since fixed-decimal formatting is common; wallets comparing amounts must therefore compare numeric values, not strings

  * at most 32 decimal places. The exact decimal value MUST correspond to a whole number of `nau`; otherwise the URI is invalid. Implementations MUST perform this check with exact decimal arithmetic. Given 1 NPT = 4 × 10^30 `nau`, a value expressed in 10^-32 NPT units corresponds to `value × 4 / 100` `nau`; therefore the integer count of 10^-32 NPT units MUST be divisible by 25. This means 32 decimal places permit every whole-`nau` amount, including 1, 2, and 3 `nau`, while rejecting finer values such as 10^-32 NPT = 0.04 `nau`. The 32-decimal limit is an intentional representation bound, not a limitation of Neptune's underlying monetary representation.

  * greater than zero and at most 42000000, the maximum supply defined for the current Neptune Cash monetary model. This limit is a protocol-level validity rule for NIP-2; if the monetary maximum changes, this NIP MUST be revised rather than silently changing the meaning of existing URIs

  * implementations MUST convert the amount to an integer number of nau using exact decimal arithmetic; binary floating point MUST NOT be used at any stage, since even 1 NPT in nau is far beyond the 2^53 exact-integer range of an IEEE 754 double, which silently rewrites conforming amounts (see the rationale)

* `label` is optional: a human-readable name identifying the intended payee, merchant, organization, or other recipient as supplied by the URI creator; it is unauthenticated. It is intended for display in the payer's wallet and is not sent to the recipient. The value is percent-encoded UTF-8 and MUST be at most 255 bytes after percent-decoding and UTF-8 validation. The limit applies to the decoded UTF-8 byte length; the percent-encoded representation may be longer. A longer decoded value makes the entire URI invalid. If the parameter is present, its decoded value MUST be non-empty.

* `message` is optional: a human-readable description of the purpose or context of the requested payment supplied by the URI creator; it is unauthenticated. It is intended for display to the payer and is not sent to the recipient. The value is percent-encoded UTF-8 and MUST be at most 255 bytes after percent-decoding and UTF-8 validation. The limit applies to the decoded UTF-8 byte length; the percent-encoded representation may be longer. A longer decoded value makes the entire URI invalid. If the parameter is present, its decoded value MUST be non-empty.

* Both `label` and `message` are unauthenticated metadata supplied by the URI creator. **Neither is transmitted on-chain nor sent to the recipient in any form. Wallets MUST NOT treat either field as authenticated information about the recipient or payment.**

* Unknown query parameters MUST be ignored (forward compatibility), except for the reserved `req-*` namespace described below.

### URI Grammar

The following ABNF defines the syntactic structure of a Neptune Cash payment URI. Semantic restrictions described elsewhere in this NIP, including address validation, network validation, amount bounds, duplicate-parameter detection, and address-type restrictions, are additional requirements and are not fully expressed by this grammar.

The grammar uses the ABNF notation defined by RFC 5234 and URI character classes from RFC 3986.

```abnf

payment-uri       = scheme ":" address [ "?" [ query ] ]

scheme            = "neptunecash"

address           = 1*address-char

address-char      = ALPHA / DIGIT

query             = parameter *( "&" parameter )
parameter         = amount-parameter / generic-parameter
amount-parameter  = "amount" "=" amount-value
generic-parameter = name "=" value

name              = 1*name-char
reserved-indexed   = ( "address" / "amount" ) "." 1*DIGIT
reserved-name      = "address" / reserved-indexed / "reference" / "memo"

amount-value      = ( "0" / ( %x31-39 *DIGIT ) ) [ "." 1*32DIGIT ]

name-char         = ALPHA / DIGIT / "-" / "." / "_" / "~"

value             = *value-char

value-char        = unreserved / pct-encoded / sub-delims-no-amp / ":" / "@" / "=" / "/" / "?"

unreserved        = ALPHA / DIGIT / "-" / "." / "_" / "~"

sub-delims-no-amp = "!" / "$" / "'" / "(" / ")" /

                    "*" / "+" / "," / ";"

pct-encoded       = "%" HEXDIG HEXDIG

ALPHA             = %x41-5A / %x61-7A

DIGIT             = %x30-39

HEXDIG            = DIGIT / %x41-46 / %x61-66
```

Parameter names consist only of the ASCII characters permitted by `name-char`. Percent-encoded characters are not permitted in parameter names; therefore parameter names cannot contain percent-encoded triplets. The `name-char` production is deliberately permissive about uppercase ASCII so that such names remain lexically well-formed; uppercase parameter names are rejected at parsing precedence step (7) as a Parameter error.

The `scheme` production is shown in lowercase for readability; scheme matching is case-insensitive as specified above.

The `address` production describes the character-level form of the address. Full bech32m validation, including checksum, HRP, network, address type, and mixed-case rules, is a semantic requirement and MUST also be performed.

The `amount` value uses the dedicated `amount-parameter` production and MUST additionally satisfy the exact amount semantic validation rules described in the `amount` section. The general `parameter` production remains useful for unknown parameters. The `amount-value` production itself does not encode the 42,000,000 bound or whole-`nau` divisibility. The `amount` value MUST NOT contain percent-encoded characters.

For `label` and `message`, the `value` production permits percent-encoded UTF-8. Percent-decoding MUST be performed exactly once as specified in the Parsing section. A decoded value MUST contain valid UTF-8 and MUST NOT exceed 255 bytes.

Literal `&` is reserved as the query-parameter separator and therefore MUST NOT appear in a parameter value. An ampersand intended as data MUST be percent-encoded as `%26`. Literal `?` and `/` are permitted inside parameter values; after the first `?` has introduced the query, neither character changes the query structure.

The first literal `=` in a parameter separates the name from the value. Subsequent literal `=` characters belong to the value. An equals sign intended as part of a value therefore does not need to be percent-encoded.

The grammar deliberately does not permit a fragment or an authority component. Consequently, forms such as `neptunecash:<address>#fragment` and `neptunecash://<address>` are not payment URIs defined by this NIP.

A parameter name MUST NOT contain a percent-encoded character. Parameter names are matched against their literal, undecoded representation.

The grammar permits unknown parameter names so that future extensions can be introduced without changing the base grammar. Their semantics are governed by the Unknown Parameters and Extension Namespace rules below.

### Unknown Parameters and Extension Namespace

NIP-2 defines three classes of parameter names:

* **Defined parameters**: `amount`, `label`, and `message`, whose semantics are specified by this NIP.
* **Required extensions**: names beginning with the exact lowercase prefix `req-`. An unsupported `req-*` parameter MUST cause the entire URI to be rejected.
* **Optional/private extensions**: names beginning with the exact lowercase prefix `x-`. An implementation that does not understand an `x-*` parameter MUST ignore it.

Unknown names outside these classes MUST be ignored, except for reserved-unassigned names, which MUST cause rejection. Unknown parameters MUST NOT change the interpretation of known parameters.

Parameter names are never percent-decoded. A `%` in a parameter name is therefore invalid under the grammar, and percent-encoding cannot be used to evade `req-`, `x-`, or defined-parameter classification.

All parameter names MUST use lowercase ASCII spelling. This rule is permanent and does not depend on the current parameter registry. Thus `Amount=1`, `AMOUNT=1`, and `Req-test=1` are invalid rather than unknown ordinary parameters. This keeps parameter validity stable when future NIPs add new defined names.

Future NIPs defining required extensions MUST use the `req-` namespace and MUST define the parameter's syntax, semantics, security considerations, and failure behavior. Future NIPs MUST NOT assign standardized semantics to names beginning with `x-`; that namespace is reserved for optional/private extensions.

The names `address`, `reference`, and `memo`, together with names matching `address.N` and `amount.N`, are reserved-unassigned by NIP-2. The indexed forms match the `reserved-indexed` production; bare `address` is reserved because it is used by other payment-URI schemes for recipient selection. They have no payment semantics in v1. A URI containing one of these reserved-unassigned names MUST be rejected. The reserved-name set is defined by the `reserved-name` production. Wallets MUST NOT assign special multi-recipient or payment-tracking semantics to them. A future NIP may define such semantics explicitly.

Examples:

```text
neptunecash:<ADDR>?futuredata=abc
```

A wallet that does not understand `futuredata` ignores it.

```text
neptunecash:<ADDR>?x-order-id=abc
```

A wallet that does not understand `x-order-id` ignores it.

```text
neptunecash:<ADDR>?req-expires=2027-01-01
```

A wallet that does not understand `req-expires` MUST reject the URI.

Duplicate-name detection applies before parameters are classified as known, unknown, `x-*`, or `req-*`.

### Standard Parameter Registry


The following table defines the standardized NIP-2 parameter namespace. New standardized parameters MUST be added to this registry before acquiring standardized semantics.

| Parameter | Status | Semantics |
|---|---|---|
| `amount` | Defined | Requested payment amount in NPT |
| `label` | Defined | Unauthenticated payer-facing recipient label |
| `message` | Defined | Unauthenticated payer-facing payment message |
| `req-*` | Reserved | Required extension namespace; unsupported members cause rejection |
| `x-*` | Reserved | Optional/private extension namespace; unsupported members are ignored |
| `address.N` | Reserved-unassigned | Reserved for possible future multi-recipient semantics; use causes rejection in v1 |
| `amount.N` | Reserved-unassigned | Reserved for possible future multi-recipient semantics; use causes rejection in v1 |
| `reference` | Reserved-unassigned | Reserved for possible future payment-reference semantics; use causes rejection in v1 |
| `memo` | Reserved-unassigned | Reserved for possible future recipient-visible payment metadata; use causes rejection in v1 |

Unknown parameters remain permitted and are ignored unless they use the reserved `req-*` namespace or are reserved-unassigned names. Unsupported `req-*` parameters and reserved-unassigned names cause rejection. Optional/private `x-*` parameters likewise have no standardized semantics unless a future application-specific convention defines them.

### Multiple Recipients

NIP-2 defines a payment URI for a **single receiving address**.

Multiple-recipient payment requests are **out of scope for version 1**. A conforming NIP-2 URI MUST contain exactly one receiving address in its URI path.

This NIP does not define indexed parameters or a separate first-recipient `address` parameter such as:

```text

address.1=

amount.1=

address.2=

amount.2=

```

A URI containing such parameters MUST be rejected; wallets MUST NOT ignore them as ordinary unknown parameters or assign special multi-recipient semantics to them.

A future NIP MAY define a multi-recipient payment-request format. Such an extension MUST define how recipients and their associated amounts are grouped, validated, displayed, and confirmed before signing.

### Payment References and Merchant Tracking

NIP-2 does not define a payment reference, invoice identifier, merchant order identifier, callback URL, or other mechanism for associating an on-chain payment with an off-chain payment request.

Payment references and merchant tracking are **out of scope for version 1**.

In particular, `label` and `message` MUST NOT be used as payment identifiers. The name `memo` is reserved for a future recipient-visible payment-metadata mechanism; it is rejected in v1 so that older wallets fail closed rather than silently dropping a future required field. They are unauthenticated, payer-facing display metadata and are not transmitted on-chain or to the recipient.

A future NIP MAY define a payment-reference mechanism. Such a mechanism SHOULD use an explicitly defined parameter and SHOULD specify how wallets preserve the reference through transaction construction and how recipients or merchants can reliably associate a transaction with the request.

Until such an extension is standardized, wallets MUST NOT assign special payment-tracking semantics to unknown parameters. The reserved name `reference` is rejected in v1 rather than ignored.

### Canonicalization

NIP-2 does not define a canonical serialized representation of a payment URI in version 1. Two different URI strings MAY represent the same semantic value after parsing. Implementations MUST NOT compare payment requests for equality by string comparison unless they explicitly intend to compare their serialized forms.

In particular:

* Parameter order is not significant.
* Percent-encoded hexadecimal digits are case-insensitive, so `%2f` and `%2F` represent the same byte.
* Known parameter values retain their parameter-specific semantics; numeric amounts MUST be compared as exact numeric values, not as strings. Thus `10`, `10.0`, and `10.00` represent the same amount.
* A literal `+` and a percent-encoded plus (`%2B`) both decode to `+` in text values, although the serialized forms are different.

Wallets SHOULD emit a stable representation when generating URIs, using the canonical lowercase scheme spelling, canonical lowercase parameter names, and a consistent parameter order. This is a generation recommendation, not a requirement that parsers reject semantically equivalent non-canonical spellings.

NIP-2 does not define URI signing, hashing, or cryptographic equivalence. A future specification that signs payment URIs MUST define its own canonicalization rules rather than relying on string equality.

## Parsing

Implementations MAY impose a maximum total URI length. If an implementation imposes such a limit, it MUST reject the URI before performing potentially expensive address decoding or other resource-intensive processing, and it MUST accept URIs of at least 8192 bytes in total length. An implementation-specific length limit is a resource/transport constraint and MUST NOT change the interpretation of URIs that are within the supported limit.

URI generators SHOULD keep generated URIs at or below 8192 bytes when practical. The 8192-byte value is an interoperability floor for parsers, not a maximum URI length. A URI composed solely of v1-defined parameters has a maximum URI length of 5089 bytes when using a Generation address. Thus, an 8192-byte implementation limit accommodates the entire defined-parameter v1 space. Unknown and `x-*` parameters have no specified length bound and may produce longer URIs; implementations may reject those once their implementation-specific limit is reached.

NIP-2 implementations SHOULD follow a parse-then-validate pipeline rather than passing the URI through a generic URL or form decoder. The intended processing model is: raw URI -> NIP-2 lexical parsing -> parameter-name validation and duplicate detection -> required-extension classification -> parameter-value decoding where specified -> UTF-8 validation -> parameter-specific semantic validation -> payment request. A generic URL parser MAY be used for preliminary transport handling only if its behavior is verified not to normalize, decode, or reinterpret NIP-2 syntax before NIP-2 validation.

Parsing proceeds in this order. Parameter names are interpreted literally and must use lowercase ASCII spelling; percent-decoding is performed exactly once on parameter values only, after query structure and parameter names have been parsed. For purposes of parsing, a parameter name is the exact sequence of URI characters from the start of a query component through the character immediately before its first `=`. Implementations MUST NOT parse the query using `application/x-www-form-urlencoded` semantics.

1\. MUST trim leading and trailing ASCII whitespace surrounding the entire URI, but MUST NOT remove or normalize whitespace occurring inside the URI. Any unescaped whitespace remaining inside the URI is invalid. Match the scheme case-insensitively; percent-encoded characters in the scheme are invalid; a URI containing a `#` is invalid.

2\. Split the remainder into address and query string at the first `?`. The address begins immediately after the scheme's colon; a URI with `//` after the colon is invalid, since these URIs have no authority component, and composers MUST NOT emit that form. Generic URL libraries parse `//` as an authority and may normalize or reinterpret it, so parsers MUST ensure that this forbidden syntax is rejected before such normalization can change the input. Validate the address's case symmetry before any case conversion: mixed-case addresses MUST be rejected, while an all-uppercase address MAY be normalized only after that check succeeds. Then validate the Bech32m checksum, HRP, address type, and network, applying the rejection precedence defined above.

3\. An empty query string (a bare trailing `?`) is valid and equivalent to no query string. Otherwise, split the query string into components on `&`, then split each component into name and value at its first `=`; literal `=` characters after the first belong to the value. An empty component (from a leading `&`, a trailing `&`, or `&&`), a component with no `=`, or an empty name makes the URI invalid.

4\. Match parameter names byte-for-byte against the literal, undecoded text. Parameter names MUST use lowercase ASCII letters, digits, `-`, `.`, `_`, and `~` only. A `%` in a parameter name is invalid. Duplicate detection compares literal names byte-for-byte. After duplicate detection, classify each name as a defined parameter, an unknown required extension (`req-*`), an unknown optional/private extension (`x-*`), a reserved-unassigned name, or another unknown parameter. Unknown `req-*` parameters and reserved-unassigned names invalidate the URI; unknown `x-*` and other unknown parameters are ignored.
5\. Validate the `amount` value against its grammar literally, with no percent-decoding; a `%` in the amount makes the URI invalid. Then convert the exact decimal value to `nau`; the conversion MUST produce an integer with no rounding. Equivalently, at 32 decimal places the integer count of 10^-32 NPT units MUST be divisible by 25.

6\. Percent-decode `label` and `message` values exactly once. A `+` is a literal plus sign, never a space: this is RFC 3986 percent-encoding, not form encoding, and composers MUST NOT use form serialization, which encodes spaces as `+`. Every `%` must be followed by exactly two hexadecimal digits, and the decoded bytes must be valid UTF-8. If percent-decoding produces a byte sequence that is not valid UTF-8, the parser MUST reject the URI. Implementations MUST NOT replace invalid byte sequences with `U+FFFD` or otherwise perform lossy conversion. A malformed escape or invalid UTF-8 makes the URI invalid. A decoded value MUST NOT be decoded again.

A known parameter that fails its parameter-specific syntax or semantic constraints MUST cause the entire URI to be rejected. A parser MUST NOT attempt to repair, coerce, or reinterpret malformed known parameters.

### Error precedence

When more than one invalid condition is present, parsers MUST evaluate and report the first applicable error according to the parsing order above. For interoperability, the precedence is: (1) input preprocessing and URI-length checks; (2) scheme and URI structure; (3) address lexical, authority, and fragment checks; (4) symmetric-address-family rejection; (5) Bech32m checksum, HRP, address type, and network validation; (6) query syntax; (7) parameter-name lexical validation; (8) duplicate-name detection; (9) reserved-name and required-extension classification; (10) parameter-value decoding and UTF-8 validation; and (11) parameter-specific semantic validation. User-facing error wording MAY differ, but the applicable error class MUST be determined in this order.

### Plus signs and spaces

The character `+` is interpreted literally and MUST NOT be converted to a space. A space in a text value MUST be represented by percent-encoding as `%20`. Implementations MUST NOT apply HTML form or `application/x-www-form-urlencoded` rules to NIP-2 query values.

For example:

```text
neptunecash:<ADDR>?label=A+B
```

contains the label `A+B`, while:

```text
neptunecash:<ADDR>?label=A%20B
```

contains the label `A B`. A literal plus MAY also be percent-encoded as `%2B`.

Valid, a conforming wallet accepts these:

* `neptunecash:<ADDR>` parses as the bare address, no parameters.

* `neptunecash:<ADDR>?` parses identically; a bare trailing `?` is equivalent to no query string.

* `neptunecash:<ADDR>?amount=1.25` parses with an amount of 1.25 NPT.

* `NEPTUNECASH:<ADDR>?amount=10&label=Dev%20Fund` parses with an amount of 10 NPT and the label `Dev Fund`; scheme matching is case-insensitive.

* `neptunecash:<ADDR-UPPER>?amount=1.25` parses; an all-uppercase address is accepted.

* `neptunecash:<ADDR-ECH>?amount=1.25&label=Caf%C3%A9` parses; EcHybrid addresses are accepted, and the label percent-decodes to `Café`.

* `neptunecash:<ADDR-VIEW>` parses as a bare viewing address.

* `neptunecash:<ADDR>?futuredata=abc&amount=2` parses with an amount of 2 NPT; the unknown parameter `futuredata` is ignored, and parameter order does not matter.

* `neptunecash:<ADDR>?x-order-id=abc&amount=2` parses with an amount of 2 NPT; the unknown optional/private `x-order-id` parameter is ignored.

* `neptunecash:<ADDR>?label=%2520` parses with the label `%20`, not a space: values are percent-decoded exactly once, never twice.

* `neptunecash:<ADDR>?amount=42000000` parses; the maximum supply is the largest permitted amount.

* `neptunecash:<ADDR>?amount=0.000000000000000000000000000001` parses; exactly 4 `nau` (10⁻³⁰ NPT).

* `neptunecash:<ADDR>?label=a+b` parses with the label `a+b`, not `a b`; a plus is a literal plus.

* `neptunecash:<ADDR>?label=a%26amount%3D9` parses with the label `a&amount=9` and no amount: values are decoded only after the query string has been split.

* `NePtUnEcAsH:<ADDR>` parses; scheme matching is case-insensitive and applies regardless of whether a query string is present.

* `neptunecash:<ADDR>?label=a?b` parses with the label `a?b`; `?` is permitted inside a value after the query has begun.

* `neptunecash:<ADDR>?label=a/b` parses with the label `a/b`; `/` is permitted inside a value.


Invalid, a conforming wallet rejects these:

* `neptunecash:?amount=1`, because the address is empty.

* `neptunecash:`, because the address is empty.

* `neptunecash:<ADDR>?req-expires=2027-01-01`, because the wallet does not recognize the `req-` prefixed parameter.

* `neptunecash:<ADDR>?amount=1&amount=2`, because a duplicated parameter name is rejected outright rather than resolved first-wins or last-wins.

* `neptunecash:<ADDR>?amount=`, because `amount` may not be empty.

* `neptunecash:<ADDR>?amount=1,25`, because the decimal separator must be `.`.

* `neptunecash:<ADDR>?amount=1e3` and `neptunecash:<ADDR>?amount=1e6`, because exponent notation is not allowed.

* `neptunecash:<ADDR>?amount=.5`, because at least one digit must precede the decimal separator.

* `neptunecash:<ADDR>?amount=-1`, because signed amounts are not allowed, even though neptune-core's own amount parser accepts them.

* `neptunecash:<ADDR>?amount=0`, because the amount must be greater than zero.

* `neptunecash:<ADDR>?amount=42000001`, because the amount exceeds the maximum supply.

* `neptunecash:<ADDR>?amount=0.0000000000000000000000000000001`, because it has 31 fractional decimal places and its exact value is 0.4 `nau`, not a whole number of `nau`.

* `neptunecash:<ADDR>?amount=1.`, because a decimal separator must be followed by at least one digit.

* `neptunecash:<ADDR>?amount=007`, because leading zeros are not allowed: the rule removes padding spellings and bounds the amount's length.

* `neptunecash:<ADDR>?amount=1%2E25`, because the amount is validated literally and may not contain percent-encoding.

* `neptunecash:<ADDR>?futuredata=1&futuredata=2`, because the duplicate rule covers unknown parameter names too.

* `neptunecash:<ADDR>?address.1=<ADDR>&amount=2`, because `address.1` is reserved-unassigned in v1.

* `neptunecash:<ADDR>?address=<ADDR>&amount=2`, because `address` is reserved-unassigned in v1.

* `neptunecash:<ADDR>?amount.1=2`, because `amount.1` is reserved-unassigned in v1.

* `neptunecash:<ADDR>?reference=abc`, because `reference` is reserved-unassigned in v1.

* `neptunecash:<ADDR>?memo=hello`, because `memo` is reserved-unassigned in v1.

* `neptunecash:<ADDR>?label=`, because a present `label` must have a non-empty decoded value.

* `neptunecash:<ADDR>?message=`, because a present `message` must have a non-empty decoded value.

* `NPT:<ADDR>?amount=1`, because the legacy `NPT:` payload is address-only and is not extended by NIP-2.

* `neptunecash:<ADDR>?%61mount=2`, because a `%` in a parameter name is invalid: names are matched literally and never percent-decoded, so `%61mount` can neither become `amount` nor slip past as ignorable.

* `neptunecash:<ADDR>?req-test=1&req-test=2`, because duplicate detection applies to required extension parameters too.

* `neptunecash:<ADDR>#donate`, because fragments are not part of this scheme and are rejected rather than stripped.

* `neptunecash://<ADDR>`, because these URIs have no authority component; `//` after the colon is invalid.

* `neptunecash:<ADDR>?amount`, because every component must contain an `=`, and `neptunecash:<ADDR>?&amount=1`, because an empty component is invalid.

* `neptunecash:<ADDR>?label=%GG`, `neptunecash:<ADDR>?label=abc%2`, and `neptunecash:<ADDR>?label=%FF`, because every `%` must be followed by exactly two hexadecimal digits and the decoded bytes must be valid UTF-8.

* A URI whose `label` or `message` percent-decodes to more than 255 bytes.

* `neptunecash:<ADDR>`, with the final character changed from `r` to `q` so the address ends `..ucsycul295xcwprq`, because the bech32m checksum fails.

* `neptunecash:<ADDR>`, with the first character of the address uppercased (`Nolgam1..`), because mixed case is invalid per bech32m.

* The first valid vector, presented to a wallet whose active network is not mainnet, because the address HRP `nolgam` does not match the active network.

* `neptunecash:<ADDR>`, with a testnet generation address (HRP `nolgat`) presented to a mainnet wallet, because the address network does not match the active network.

* A URI whose address is a symmetric-key address (HRP `nsymkm`), because that address type is banned. The concrete vector will be generated from a throwaway seed alongside the reference parser, since even an example symmetric address is a spending key.

* A URI carrying a syntactically valid bech32m string whose HRP is outside the table above, for example an address of the XNT fork (`xntnw` plus a network character), because unknown address types are rejected.

## Error classifications

NIP-2 does not mandate implementation-specific error-code strings. Implementations MAY expose their own machine-readable codes and user-facing messages. For interoperability and diagnostics, implementations SHOULD classify failures using the following conceptual categories.
| Error class | Typical triggers |
|---|---|
| Syntax error | Malformed URI syntax, forbidden authority (`//`), fragment, internal unescaped whitespace, empty query components, missing `=` |
| Address error | Invalid Bech32m encoding/checksum, unknown address type, forbidden symmetric-key address, mixed-case address |
| Network mismatch | Recognized address type whose network character does not match the active network |
| Parameter error | Duplicate parameter name, malformed known parameter, invalid parameter name, uppercase or otherwise invalid parameter name |
| Required-extension error | Unsupported `req-*` parameter |
| Encoding error | Malformed percent-encoding or invalid UTF-8 after decoding |
| Amount error | Zero amount, amount above 42,000,000 NPT, non-integral-`nau` amount, excessive decimal precision, invalid amount syntax |

The numeric value represented by `amount` MUST be greater than zero and MUST NOT exceed 42,000,000 NPT. The value MUST correspond exactly to a whole number of `nau`. Because 1 NPT = 4 × 10³⁰ `nau`, one `nau` equals 25 × 10⁻³² NPT.

Implementations SHOULD distinguish address-type rejection, network mismatch, duplicate parameters, unsupported required extensions, malformed encoding, and invalid amounts in diagnostics even when their public API maps several of these to a broader error type.

# Conformance

The normative machine-readable conformance artifact for NIP-2 is `vectors.json`. Implementations SHOULD run these vectors against the reference parser and SHOULD report the expected conceptual error class when a vector is rejected.

A conforming NIP-2 parser MUST:

1. Recognize the `neptunecash` scheme case-insensitively.
2. Trim leading and trailing ASCII whitespace around the entire URI, but MUST reject any unescaped whitespace remaining inside the URI.
3. Reject an authority component (`//`).
4. Parse exactly one receiving address.
5. Validate the address as a permitted Neptune Cash bech32m address, including checksum, HRP, network, address type, and mixed-case rules.
6. Reject the symmetric-key address family.
7. Accept a bare trailing `?` as equivalent to no query.
8. Reject fragments.
9. Split query parameters on literal `&` and each parameter on its first literal `=`.
10. Reject empty parameter components and parameters without `=`.
11. Treat parameter names literally; parameter names MUST use lowercase ASCII spelling only.
12. Reject percent-encoded characters in parameter names.
13. Detect duplicate parameter names before discarding unknown parameters.
14. Treat `+` as a literal plus and never as a space.
15. Validate percent-encoding and decode parameter values at most once, only where the parameter definition requires decoding.
16. Reject invalid UTF-8 after decoding text parameters.
17. Validate known parameters according to their parameter-specific syntax and semantic constraints; malformed known parameters MUST cause rejection.
18. Reject reserved-unassigned parameter names; ignore unknown parameters outside reserved namespaces.
19. Reject unsupported parameters whose name begins with the exact lowercase `req-`; ignore unsupported parameters whose name begins with the exact lowercase `x-`.
20. Apply the exact amount rules, including bounds, 32-decimal precision, and exact whole-`nau` representability, without binary floating-point conversion.

A conforming NIP-2 wallet MUST:

1. Display the decoded destination and requested amount, when present, before authorization.
2. Treat `label` and `message` as untrusted metadata.
3. Require explicit user confirmation before signing or broadcasting a payment.
4. MUST NOT silently alter a requested `amount`; any user override MUST be explicit and visible.
5. Apply the address-reuse and delivery-context restrictions defined by this NIP when generating payment requests.
6. Warn the user before generating a URI containing a `ViewingAddress` or `EcHybrid` address, explaining that the address is intended for a single counterparty and should not be publicly or repeatedly distributed.

A conforming NIP-2 URI generator MUST:

1. Encode requested amounts using exact decimal arithmetic and MUST NOT round, truncate, or otherwise alter an amount to make it representable.
2. Report an amount as unrepresentable if its exact value does not correspond to a whole number of `nau` within the NIP-2 amount constraints.
3. Percent-encode text values as required by this NIP and MUST NOT use `application/x-www-form-urlencoded` space-as-`+` serialization.

A wallet MAY provide additional policy checks, warnings, or user-interface protections, provided they do not weaken the parser or wallet requirements above.

# QR code guidance

Two independent limits govern QR encoding of these URIs: symbol capacity and scannability.

**Capacity.** The QR alphanumeric character set contains `:` but not `?`, `=`, or `&`, so the uppercase scheme and all-uppercase address portion can be encoded using QR alphanumeric mode while any query string cannot.

* An address-only generation payload (`NEPTUNECASH:` plus the uppercased 3482-character address, 3494 characters in total) requires error correction level L: no level M symbol of any version can hold it, since alphanumeric capacity at level M peaks at 3391 characters. At level L it fits from version 36 (capacity 3537 characters, 161x161 modules) through version 40 (capacity 4296 characters, 177x177 modules).

* A parameterized generation URI still fits at version 40 level L, but only with mixed-mode segmentation: an alphanumeric segment for the scheme and uppercased address (19,234 of the 23,648 available data bits) and a byte-mode segment for the query string, leaving at most 549 bytes for parameters. A single-segment encoder, one that does not perform explicit mixed-mode segmentation, drops the whole string to byte mode the moment it sees `?` and fails, because version 40 byte capacity at level L is 2953 bytes. Wallets generating QR codes MUST use an encoding method capable of representing the complete URI without altering its contents; where mixed-mode segmentation is required to fit the URI, the generator MUST support it or use a larger supported QR configuration. If the complete URI cannot be represented, the wallet MUST provide a non-QR representation of the complete URI rather than emit a truncated or altered QR payload.

* EcHybrid (168 characters) and viewing (116 characters) addresses never need segmentation: even the worst case the grammar permits (an amount at its maximum post-validation length of 41 characters, 8 integer digits plus the separator plus 32 decimal places, and `label` and `message` each at 255 bytes, fully percent-encoded to 765 characters) is a 1775-byte URI. Version 31 at level L (141x141 modules) is the first symbol whose single-segment byte-mode capacity holds it: version 30 at level L holds 1732 bytes, version 31 holds 1840. For a concrete point of reference, the EcHybrid test vector above, `neptunecash:<ADDR-ECH>?amount=1.25&label=Caf%C3%A9` (208 bytes), fits a version 9 symbol at level L (53x53 modules).

**Scannability.** A version 36 to 40 symbol is 161x161 to 177x177 modules and demands both physical size and camera quality. Wallets SHOULD select an address type appropriate to the delivery context. Generation addresses are RECOMMENDED for payment requests intended for broad or repeated distribution, while EcHybrid and ViewingAddress addresses MAY be used for requests delivered directly to a known single counterparty, subject to the reuse rules under Security Considerations. Wallets SHOULD render generation-address QR codes large. When a complete QR encoding is impractical, wallets SHOULD offer a copyable link or other non-QR representation.

For a published or reusable request, a generation address is the appropriate type, since wallets MUST NOT present the other allowed types as public or reusable requests (see security considerations); the choice there is between a large dense QR code and a plain link.

# Handler registration

Wallets that support opening links or deep links SHOULD register as the OS-level handler for the `neptunecash:` scheme, if no other handler is already registered, so that such links open a pre-filled send screen:

* Windows: a registry key `HKEY_CLASSES_ROOT\neptunecash` with an empty `URL Protocol` value and a `shell\open\command` entry.

* macOS: `CFBundleURLTypes` in the app bundle's `Info.plist`.

* Linux: a `.desktop` file declaring `MimeType=x-scheme-handler/neptunecash;`.

* Android: an `<intent-filter>` with `<data android:scheme="neptunecash" />`.

* iOS: `CFBundleURLSchemes` in `Info.plist`.

No allowlist exists at the OS level; any scheme string can be registered, which is how `bitcoin:` and `monero:` links work today. Two browser caveats do apply:

* Browsers gate navigation to unknown schemes behind user activation and usually a confirmation prompt, and block it entirely from some contexts such as sandboxed iframes. This affects every cryptocurrency scheme equally.

* The JavaScript API `navigator.registerProtocolHandler`, which lets a website rather than a native app claim a scheme, is restricted to a [safelist](https://html.spec.whatwg.org/multipage/system-state.html#safelisted-scheme) plus schemes prefixed `web+`. The safelist includes `bitcoin` but not `monero` or `zcash`. A browser-hosted Neptune Cash wallet would therefore have to use `web+neptunecash:`, or the scheme would need to be added to the safelist by a spec change, as `bitcoin` was. This NIP notes the constraint but does not reserve `web+neptunecash:`; no browser-hosted wallet exists today.

Scheme registration itself is unauthenticated: another installed application, including one impersonating a wallet, can claim `neptunecash:` and receive the URIs the user opens. Nothing in this spec therefore treats delivery of a URI as trusted, and this is a second reason a URI must never carry a secret (see the symmetric-address rule). A wallet that finds another application already registered SHOULD alert the user once rather than silently seizing the registration, the same etiquette Stellar's SEP-0007 specifies for this threat.

# Parser and wallet responsibilities

This NIP distinguishes protocol parsing from wallet policy.

A **parser** determines whether a URI conforms to NIP-2 syntax and semantics. It MUST enforce the normative rejection, duplicate-detection, case, encoding, and parameter-validation rules in this document. A parser does not need to decide whether a user should trust the URI creator.

A **wallet** consumes the parsed payment request and applies wallet-level security and user-interface policy. The wallet MUST display the decoded destination and amount when present, MUST treat `label` and `message` as untrusted metadata, and MUST require explicit confirmation before signing or broadcasting. Wallet policy MAY impose stricter restrictions, such as refusing certain address types for public QR generation.

A library implementation SHOULD expose parsing errors separately from wallet-policy warnings so that applications can distinguish malformed payment URIs from otherwise valid requests that a particular wallet chooses not to use.

# Security considerations

A payment URI is untrusted input: it arrives from web pages, chat messages, and scanned QR codes, none of which the wallet controls.

* **Confirmation.** The wallet MUST display the decoded address and, if present, the amount, and require explicit user confirmation before signing or broadcasting a transaction. Opening a URI MUST NOT by itself authorize or send a payment, however the URI arrived.

* **Untrusted text.** `label` and `message` are attacker-chosen strings and MUST be rendered inert: no markup interpretation, control characters stripped or escaped, and bidirectional override characters such as U+202E neutralized (these are Unicode format characters rather than controls, and can visually reverse displayed text), and truncation made visible rather than silent. Homoglyphs make `label` unsuitable as the sole identifier of a payee; the address is the identity, the label is a hint. Wallets MUST NOT treat `label` or `message` as authenticated information about the recipient, and MUST NOT use either parameter to determine the destination address.

* **Network mismatch.** As specified above, an address whose HRP does not match the active network MUST be rejected as a network mismatch. Addresses of the XNT fork are rejected as unknown address types, since their HRP family is not defined by this NIP.

* **The symmetric address family.** A raw symmetric-key encoding is the secret key; a digest-only display string shares the same HRP, which is why the whole family is rejected rather than told apart. Beyond the MUST NOT in the specification, implementers should know why this is easy to get wrong: neptune-core's generic `ReceivingAddress::to_bech32m` returns the raw key material for the symmetric variant, and its own documentation warns that it must never be used for display. A wallet that builds URIs by calling the generic encoder over an arbitrary receiving address will leak a spending key the moment a symmetric address reaches it; match on the address type explicitly. On the parsing side, a URI carrying an `nsymk`-family address MUST be rejected before it is displayed or used for payment, and once the family is recognized the wallet MUST NOT intentionally persist or log the raw URI or address, including in wallet-controlled clipboard or history features, telemetry, crash reports, or diagnostic output.

* **Reuse-sensitive address types.** Wallets MUST NOT present an EcHybrid or viewing address as a public or reusable payment request; these types MAY be used for a request intended for a single counterparty. Anyone who knows a viewing address can read that address's entire on-chain transaction history (when on-chain announcements are used), and an EcHybrid address gives the same power to an attacker with a quantum computer. No parser can detect wider sharing after the fact, since the hazard lies in how widely the string is shared, not in the string itself; the enforceable levers sit with the wallet that creates the URI, which MUST warn the user at generation time that the address is intended for a single payer.

Wallets SHOULD avoid unnecessary persistence or logging of EcHybrid and ViewingAddress payment URIs, including in wallet-controlled history, telemetry, crash reports, and diagnostics. If such data must be retained for an operational purpose, wallets SHOULD make that retention explicit and minimize its scope.

# Rationale

NIP-2 treats malformed or over-limit metadata as a URI validation failure rather than silently truncating or discarding it, so that the URI has one deterministic interpretation across implementations.

### Case sensitivity

Parameter names use lowercase ASCII only. This gives each parameter a single stable spelling and makes misspelled names fail rather than silently acquiring a different interpretation. The rule is independent of how other cryptocurrency payment schemes handle parameter names; those schemes were useful references, but NIP-2 chooses its parameter syntax according to Neptune's own interoperability and safety requirements.

### Scheme name

The wallets' existing QR payloads use `NPT:`, and extending that payload was an option, but a fully spelled-out scheme name is preferable: other cryptocurrencies consistently use their project name (`bitcoin:`, `zcash:`, `monero:`), not their ticker.

A bare `neptune:` was the initial proposal, but the project name is "Neptune Cash", not "Neptune", and the name "Neptune" is contested: Neptune Privacy (XNT) is a live fork that also presents itself as Neptune. This is not a funds-safety concern, because the two chains use distinct bech32m HRPs (`nolga` plus a network character in neptune-core, `xntnw` plus a network character in xnt-core), so an XNT address presented to a Neptune wallet is rejected as an unknown address type rather than being interpreted as a Neptune address. The collision is narrower but real: OS-level URI handler registration is a single global namespace per scheme, so if both projects ship wallets registering `neptune:`, which application receives a click-to-pay link becomes contested and platform-dependent, and a user with both installed can get the wrong app.

`neptunecash:` is therefore the more faithful application of the project-name convention, not a departure from it, and the comparison table at the end of this document already records the precedent: Bitcoin Cash uses `bitcoincash:`, not `bitcoin:`. The cost is 4 extra characters in the QR payload, negligible next to a generation address of roughly 3500 characters and irrelevant for links.

**Resolution**: `neptunecash:` is primary for links and deep-linking. The decision is based on the project-specific name and avoidance of a potential OS-level URI-handler collision with another project using `neptune:`. The development-channel poll and maintainer approval are historical context, not the technical basis for the protocol decision. The legacy address-only `npt:` payload remains an optional compatibility choice for wallets that already ship it, since it is a wallet-specific convention this spec does not standardize.

## QR-code capacity

For QR alphanumeric-mode optimization, a bare payment URI (with no query string) MAY be emitted entirely in uppercase, including the scheme and address. A parameterized URI contains `?`, `=`, or `&`, which are not part of the QR alphanumeric character set and therefore require Byte mode; uppercasing the parameterized URI does not make it eligible for alphanumeric mode.

QR-code capacity is not a validity requirement of NIP-2. A valid payment URI may be too large for a QR symbol at a particular error-correction level or version. Wallets SHOULD fall back to a copyable link or other transport when the URI exceeds practical QR capacity.

## QR capacity vs. address length

Generation addresses are long enough to strain practical QR code density. Options considered: recommend the shorter address types for QR use where acceptable; accept large QR codes; or additionally spec an out-of-band form where the URI carries a URL from which the full payment request is fetched (BIP72-style).

**Resolution**, from the [RFC discussion](https://github.com/Neptune-Crypto/neptune-core/issues/959): recommend the shorter address types for QR use, and also accept the large QR codes needed to encode generation addresses; the QR code guidance section above is the normative outcome. Fetchable payment requests stay out of scope for v1 and can be revisited in a later NIP.

When generating a QR code, wallets SHOULD avoid unnecessarily long `label` and `message` values when a shorter value conveys the same information. This recommendation is a transport consideration and does not change the validity limits of NIP-2.

### Amount

The NIP-2 amount is expressed in whole NPT with a decimal fraction rather than directly in `nau`. This follows familiar human-facing payment URI practice while retaining exact conversion to Neptune's atomic unit.

The atomic-unit relationship and monetary model cited here are pinned to the Neptune Core revision referenced by this NIP; the source documentation states that one Neptune Coin equals 10^30 × 2^2 `nau` and that the current maximum supply is 42,000,000 Neptune Coins.
Neptune Core defines 1 NPT as 4 × 10^30 `nau`, so 1 `nau` equals 2.5 × 10^-31 NPT. A 32-decimal representation can therefore express every whole-`nau` amount, but not every possible 10^-32 NPT decimal. NIP-2 resolves this by requiring the exact decimal amount to convert to an integer number of `nau`; equivalently, when expressed as an integer number of 10^-32 NPT units, that integer must be divisible by 25. This permits 1, 2, and 3 `nau` while rejecting values such as 10^-32 NPT (0.04 `nau`).

This 32-decimal limit is an intentional serialization bound, not a mathematical consequence of the atomic-unit conversion. The exact whole-`nau` divisibility rule is what permits full `nau` granularity within the 32-character fractional bound. A URI generator MUST NOT round, truncate, or otherwise alter an amount to make it representable. If the requested amount does not correspond exactly to a whole number of `nau`, the generator MUST report the amount as unrepresentable.

When present, `amount` is a requested amount, not a silently editable default. A wallet MUST NOT silently alter it; if the wallet permits an override, the override MUST be an explicit and visible user action.

The exact-arithmetic requirement is particularly important because Neptune's maximum monetary amount corresponds to roughly 1.68 × 10^38 `nau`, far beyond the exact-integer range of IEEE 754 binary64 values. The NIP therefore requires exact decimal-to-`nau` conversion rather than floating-point parsing.

The 42,000,000 NPT upper bound is intentionally a NIP-2 validity rule. If Neptune Cash monetary policy changes this maximum, NIP-2 MUST be revised rather than silently changing the validity of existing URIs.

The exact-arithmetic requirement has no counterpart in BIP 21 or ZIP 321 because those chains never needed one: Bitcoin's and Zcash's maximum supplies are about 2.1 × 10^15 atomic units, inside the 2^53 range an IEEE 754 double represents exactly, while Neptune Cash's maximum supply is 1.68 × 10^38 nau. Float parsing can silently change conforming amounts in Neptune Cash while remaining harmless for those chains, which is why this specification must state explicitly what its ancestors could leave unsaid.

### Metadata length caps

BIP 21 and ZIP 321 set no maximum length for `label` or `message`, so each wallet invents its own limit and they diverge. The cap here exists so that validity is deterministic across wallets and implementations can bound what they store and render; the value 255 bytes is chosen for familiarity, not necessity, and can be revisited while this NIP is a Draft.

### Symmetric addresses

Excluded deliberately, not by omission. A raw symmetric-key encoding is the secret key itself, so a payment URI carrying one would hand spending power to everyone who sees the URI; the whole `nsymk` HRP family is rejected because digest-only display strings share it, and no parser should be in the business of telling the two apart. This is recorded here so that a future implementer does not add symmetric support back in the belief that it was overlooked.

### Multiple recipients

Multiple recipients are intentionally excluded from NIP-2 to keep the v1 payment URI model simple and unambiguous.

Zcash ZIP-321 demonstrates that a URI can represent multiple recipients through indexed parameters such as `address.1` and `amount.1`. That model is useful for more advanced payment requests, but it introduces additional grouping, validation, and user-interface semantics that are not necessary for the basic Neptune Cash payment URI.

A future NIP can define such a mechanism without changing the single-recipient semantics of NIP-2.


### Recipient-visible memo metadata

NIP-2 defines `message` as payer-facing display metadata only; it is not transmitted on-chain and is never sent to the recipient. NIP-2 therefore does not map `message` to a recipient-visible memo field. The name `memo` is reserved-unassigned in v1 and a URI containing it is rejected. This fail-closed choice ensures that an older wallet cannot silently omit a future recipient-required field while still making the payment, and leaves a future NIP free to define explicit recipient-visible semantics without creating an ambiguous compatibility mapping.

### Payment references and merchant tracking

Merchant workflows may eventually need an identifier that lets a recipient associate an on-chain transaction with an off-chain invoice or order.

Solana Pay provides a precedent for this through its `reference` mechanism, while other payment URI schemes provide related mechanisms through extensions or payment-request protocols.

NIP-2 deliberately does not define such a mechanism. `label` and `message` are display-only metadata and MUST NOT be repurposed as payment identifiers.

Deferring this functionality keeps the v1 URI small and avoids defining tracking semantics before Neptune Cash has a standardized payment-reference mechanism.
